# 运维部署与压测手册

## 1. 本地启动

在项目根目录执行：

```powershell
docker-compose up -d --build
docker-compose ps
```

统一入口为 `http://127.0.0.1:8088`：

- 状态页：`http://127.0.0.1:8088/`
- 健康检查：`http://127.0.0.1:8088/api/health`
- 状态数据：`http://127.0.0.1:8088/api/v1/status`
- 请求指标：`http://127.0.0.1:8088/api/v1/metrics/summary?windowSeconds=300`
- Redis 缓存统计：`http://127.0.0.1:8088/api/v1/metrics/cache`

状态页下方的“运维概览”会直接展示在线服务器数、平均 CPU、QPS、P99、5xx 和每台服务器最近一次上报的 CPU/内存/磁盘使用率；它与状态页共用同一套 API，不需要单独部署第二个前端。

连续访问 `/api/v1/metrics/servers/{serverId}` 会触发 Cache-Aside 读取：第一次通常从 MySQL 回源并写 Redis，后续读取命中 Redis。`/api/v1/metrics/cache` 返回 hits、misses、errors、totalReads 和 hitRate，可用于对比缓存前后的响应延迟。

可以直接运行缓存对比脚本：

```powershell
./ops/cache-benchmark.ps1 -BaseUrl http://127.0.0.1:8088 -ServerId local-compose
```

脚本会先清除指定服务器的 Redis Key，测量 MySQL 回源的未命中延迟，再测量连续命中 Redis 的延迟。实际结果会受本机 Docker、网络和数据库负载影响，应重点观察趋势而不是只看一次结果。

本机 Docker 网关的一次实测结果为：未命中 3 次平均 56.14ms，命中 20 次平均 4.81ms，命中最快 3.86ms，最慢 8.13ms；说明在当前数据规模和本机环境下，Redis 能明显减少重复读取的响应时间。

Compose 已配置 MySQL、Redis、RabbitMQ 的健康检查，后端会在依赖健康后启动；后端本身使用 `restart: unless-stopped` 防止偶发启动竞态。

MongoDB 也由 Compose 启动，供文档型数据和 MongoDB Compass 练习使用：`mongodb://root:change-me@127.0.0.1:27019/?authSource=admin`。项目核心快照当前使用 MySQL，MongoDB 作为非关系型数据库实践环境，避免为了演示而重复存储同一份业务数据。

生产环境不要继续使用 Compose 中的默认值，先复制 `.env.example` 为 `.env` 并替换强密码；正式上线步骤见 [上线配置模板](上线配置模板.md)。

## 2. WSL 与 SSH

推荐在 WSL2 中运行 Linux 采集器和服务器巡检脚本，Windows 端运行 Docker Desktop。Docker Desktop 设置中开启 WSL Integration 后，WSL 可以直接使用 `docker` 命令。

```bash
python3 collector/collector.py --server-id wsl-dev --api-url http://host.docker.internal:8088
bash scripts/server-inspect.sh user@server /path/to/id_ed25519
```

Windows PowerShell 等价脚本见 `scripts/remote-inspect.ps1`。SSH Tunnel 用于只暴露服务器本机端口：

```powershell
./scripts/ssh-tunnel.ps1 -SshHost 203.0.113.10 -User ubuntu -LocalPort 8088 -RemotePort 8088 -IdentityFile $env:USERPROFILE\.ssh\id_ed25519
```

建立隧道后，本机访问 `http://127.0.0.1:8088`，数据实际通过加密 SSH 连接转发到服务器。

## 3. 性能指标

后端会记录最近 15 分钟 API 请求的本地样本，并提供：

- QPS：窗口内请求数 / 窗口秒数
- P50：一半请求不超过该延迟
- P90：90% 请求不超过该延迟
- P99：99% 请求不超过该延迟，用于观察长尾
- P999：99.9% 请求不超过该延迟，用于发现极端慢请求

执行 k6 压测：

```bash
k6 run -e BASE_URL=http://127.0.0.1:8088 tests/k6/monitor.js
```

压测后重新访问指标接口，结合 `docker stats --no-stream` 判断 CPU、内存、数据库连接和网关是否成为瓶颈。不要直接对公网生产域名进行压测。

## 4. 日报与告警

`ops/health-report.py` 会聚合健康状态、在线服务器数、活动事件、QPS、P50/P90/P99/P999、Redis 命中率和 Docker 资源。脚本默认只本地输出；只有显式增加 `--send-feishu` 并配置 `FEISHU_WEBHOOK_URL` 才发送到飞书群。Linux systemd 示例已放在 `ops/sentinel-daily-report.*`。

正式邮件系统需要先准备邮件域名 DNS（MX、SPF、DKIM、DMARC）和 SMTP 凭据，再把告警消费者中的 TODO 接到邮件服务；任何密码、Webhook、私钥都只通过环境变量或 Secret 注入。

多域名反向代理模板位于 `infra/nginx/multi-domain.conf.example`：`api.example.com` 转发后端，`status.example.com` 转发状态页。正式部署时把真实域名、证书和 DNS 记录替换进去，并让公网只暴露 80/443。
